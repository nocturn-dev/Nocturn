## 14. Медиа-волна 2: YouTube-плеер + Ambient Lyrics (набросок, 01.10)

### YouTube-плеер внутри Nocturn (следующая волна, решение владельца)
Цель: смотреть YouTube, не покидая Nocturn (без Alt+Tab), с возможностью
свернуть в мини-бар.
- **Плеер**: embed-iframe (youtube-nocookie.com) в отдельной панели/окне —
  по образцу ArtifactsPanel (sandbox без allow-same-origin не подходит:
  YouTube-плееру нужны скрипты + postMessage → отдельный iframe с
  `allow-scripts allow-presentation`, без allow-same-origin).
- **Управление**: YouTube IFrame API (play/pause/seek/переключ видео) —
  кнопки минибара расширяются: у YouTube-источника — прогресс-бар.
- **Сворачиваемость**: панель ↔ мини-бар (полоска с названием + play/pause +
  прогресс), разворот кнопкой. Не Alt+Tab — всё внутри Nocturn.
- **CSP**: `frame-src += https://www.youtube-nocookie.com https://www.youtube.com`
  — единственное расширение периметра; остальные YouTube-домены не нужны.
- **Opt-in**: карточка YouTube в «Интеграциях» (иконка + название, паттерн
  Spotify), по умолчанию выключена.
- **Минусы**: iframe грузит внешние скрипты Google (задокументировать в
  SECURITY.md), autoplay-политики браузера требуют user-gesture, отвлечение —
  поэтому сворачивание обязательно.

### Ambient Lyrics (идея с скрина, 50/50)
Лирика как часть ambient-сцены: строки плавают в фикс-зонах поверх
процедурного фона; кинетическая типографика — полупрозрачные зоны,
медленный сдвиг, растворение в частицах при смене фраз.
- **Плюс**: запредельно стильный визуальный ход, ни у кого из конкурентов нет.
- **Минусы**: удар по фокусу (яркие строки дергают боковое зрение во время
  работы), читаемость на процедурном фоне (нужны маски/тени/glow),
  производительность слоя.
- **Когда**: после медиа-волны, если фича зайдет; реализовывать как режим
  сцены AmbientLayer (stars/fog/city → lyrics), а не отдельный слой.
- **ПИВОТ 02.10 (по волне 1)**: лента — режим Spotify/YouTube-интеграции,
  а НЕ ambient-сцен; ambient-фон остаётся как есть. Отдельный слой
  LyricsRibbon (статичный canvas без rAF), тумблер и слайдер размера —
  во вкладке «Интеграции» рядом с лирикой (mediaPrefs.ribbon/ribbonScale).
  ВОЛНА 2 — СДЕЛАНА 03.10 (cc6eb23 «за интерфейсом», 2bb55a1
  «авто-продвижение», 6b86b6b «кроссфейд»); все четыре коррекции ниже
  проверены аудитом 03.10 как выполненные. WIP в stash остаётся
  РЕФЕРЕНСОМ, применять не нужно.
  КОРРЕКЦИИ ПО АУДИТУ КОДА (03.10) — учтены в реализованной волне 2:
  - Каскад из хендоффа неверен: специфичность НЕ равна — ambient-правило

  - Кроссфейд в stash — полу-кроссфейд (старая строка гаснет мгновенно,

  - Уже закрыто 03.10 до волны 2: ytLyrics доезжает до снапшота (лента
    больше не Spotify-only), дедуп снапшота — по идентичности набора,
    цвета ленты — токены темы (accent/muted) с перерисовкой на смене
    темы, мёртвый код волны 1 из AmbientLayer удалён.
- **План реализации (уточнение 02.10 — набросок выше был слишком общим:
  не закрывал сцену-старт, источник строк, пустое состояние, технологию,
  читаемость и производительность — реализовывать по нему было нельзя):**
  1. Режим сцены `lyrics` в существующем AmbientLayer — НЕ отдельный слой:
     строки рисуются тем же canvas'ом поверх звёзд/тумана (город — самый
     дорогой, оставляем напоследок). Выбор сцен — существующий селектор.
  2. Источник строк — готовый конвейер минибара (lrclib, тумблер лирики).
     Пустое состояние: нет музыки/лирики — сцена рисует обычный ambient
     (гейт по наличию данных, отдельного тумблера включения не нужно).
  3. Технология — 2D canvas, НЕ WebGL-шейдер: строки живут в ФИКСИРОВАННЫХ
     слотах (решение владельца 02.10, референс от Nano Banana: рандом
     отброшен — может вылезать за поля). Лента времени: активная строка
     в якорной зоне, соседние строки из LRC-таймлайна занимают соседние
     слоты выше/ниже и гаснут+расплываются по удалённости от активной
     (blur по слоту; фолбэк без ctx.filter — только альфа). Смена активной
     строки — кроссфейд; распад в частицы из наброска — опциональный
     акцент, решим по живому референсу в процессе.
  3б. Регулятор размера (решение владельца): один слайдер «Размер строк»
     (масштаб ~0.3–1.0) задаёт кегль И вертикальный размах ленты — от
     компактной полоски до «на весь экран как на референсе». Поле в
     Appearance.lyricsScale (дефолт ~0.6), слайдер в «Интеграциях» рядом
     с тумблером лирики; не забыть parseProfile (урок themeProfiles).
  3в. Композер: центральная полоса резервируется — активная строка садится
     НАД композером (как на референсе); полоса зависит от состояния
     композера (центрирован на пустом чате / внизу при сообщениях) —
     AmbientLayer получает границу полосы пропом.
  4. Читаемость: полупрозрачная подложка строки — предрасчитанный
     градиент, НЕ backdrop-filter (дорого); цвет — accent + muted темы
     (сцены и так перерисовываются от палитры); reduce-motion глушит
     дрейф и частицы (статичная подсветка текущей строки).
  5. Производительность: один rAF на всё (ambient уже живёт всегда —
     §11), частицы спавнятся только на смене строки, пауза при скрытом
     окне уже есть.
  Оценка: M (2–3 вечера). Точка входа — AmbientLayer + mediaPrefs.

#### Требования владельца (02.10, записано с его слов)

   личку владельцу:
   - **начало работы** (задача запущена: название задачи, модель);
   - **конец работы** (завершена/остановлена/ошибка — как тосты
     финализации сейчас);
   - **триггеры, которые задал пользователь** — настраиваемые события,
     например: ожидание подтверждения (ask_user/confirm), срабатывание
     Hard Limit, ошибка прогона. Минимум — три встроенных тумблера в
     настройках + свободные пользовательские триггеры.
2. **Управление чатом из TG с телефона** (если возможно; владелец точно
   не знает, механику проверить в первую очередь): удалённые команды
   агенту из Telegram-переписки с ботом — отправить задачу/поправку,
   ответить на ask_user, Stop. Вопросы к проработке: bot long-polling
   (без webhook — не нужен публичный URL) vs bridge-процесс, чей токен
   и чей chat_id (привязка «бот → владелец» по первому /start),
   безопасность (токен в vault, команды только от verifed chat_id),
   связь с однопрогонным движком (очередь, activeRunRef-гейты).

## 22. Symlink-hardening записи (SECURITY.md residual, закрыто 04.10)

СДЕЛАНО: агентная запись fs_write переведена на схему «open → verify → write»
(п. «Known residual risks» SECURITY.md переехал в closed). fsutil::
open_write_verified — открытие с отказом от финального симлинка (O_NOFOLLOW /
FILE_FLAG_OPEN_REPARSE_POINT + отказ по атрибуту reparse), финальный путь
читается с ДЕСКРИПТОРА (/proc/self/fd, F_GETPATH, GetFinalPathNameByHandle)
и сверяется с ожиданием; perm::recheck_location повторяет все path-гейты
(конфиг, .env-бэкстоп, sensitive, корни) по настоящему адресу. «До» для
диффа тоже читается через дескриптор (та же гонка). Репортаж модели —
display_path (вербатим-префикс срезан). Остатки: O_CREAT-мусор при отказе
(тот же юзер) и чтения по-прежнему следуют симлинкам — принято, задокументировано.
Тесты: рандтрип, отказ финального симлинка, резолв симлинк-родителя
(unix-ветки; Windows-варианты скипаются без привилегий локально, CI-раннеры
возвышенны). Обычные конфиг-записи (atomic_write) не харднились: их пути не
агент-контролируемы, rename по финальному симлинку его ЗАМЕНЯЕТ, а не следует.

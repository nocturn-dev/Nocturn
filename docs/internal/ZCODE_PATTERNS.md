## Контекст

ZCode — Electron-приложение с аккаунтом и облаком (OAuth z.ai, GLM-модели,
телеметрия). Nocturn — локальный BYOK без единого исходящего без ведома
пользователя. Переносим **только паттерны**, совместимые с local-first:
никакой телеметрии, OAuth-аккаунтности, phone-home и облачных каналов.

## Облачный периметр ZCode (чтобы не тащить случайно)

- Телеметрия: продуктовые события на вендор-эндпоинт + ARMS RUM (Alibaba):
  perf, webvitals, исключения, whiteScreen, api-вызовы, ресурсы; OTLP
  в алиюновский регион с зашитым лицензионным ключом.
- Постоянный telemetry-user-id, выводимый из расшифрованных OAuth-кредитов
  (телеметрия привязана к аккаунту).
- Автоапдейтер, стучащийся в CDN вендора.
- Каналы уведомлений: telegram/webhook/feishu/lark/weixin/discord/wecom.
- Модель-провайдер зашит на вендорский GLM-эндпоинт (anthropic-compat).

## Паттерн 1 — Изоляция агента и планировщика в отдельных процессах

**ZCode:** главный процесс только координирует; агентный движок и
планировщик (расписания + идл-очередь) живут в отдельных ОС-процессах
(Electron utilityProcess), связь — message-channel RPC. Краш агента не
задевает UI, тяжёлые циклы не блокируют окно.

**Nocturn:** один Rust-бэкенд, движок в том же процессе (tokio). Для
однопрогонной схемы достаточно; при фоновых прогонах (план, п.6) —
выделить прогонам отдельный tokio-воркер-пул или процесс.

**Вердикт:** адаптировать при фоновых агентах. Не переписывать сейчас.

## Паттерн 2 — Git-чекпоинты с отдельным index-каталогом

**ZCode:** чекпоинты — настоящий git: собственный index-каталог вне
пользовательского `.git`, коммиты от ботового автора-константы. Диффы,
откат и история бесплатно из git-пламбминга.

**Nocturn:** файловые снапшоты + `.meta.json`-сайдкары (atomic_write);
список читает сайдкары, полный парс — фолбэк.

**Вердикт:** переносить как opt-in режим рядом со снапшотами (план, п.2):
для репо-проектов git даёт диффы и откаты, для вне-git папок остаются
снапшоты. Ботового автора называть своим именем.

## Паттерн 3 — Порядковые батчи потока событий (seq + reason)

**ZCode:** хост копит операции потока, нумерует по порядку и отдаёт UI
батчами с составным eventId (workspace/task/run/номер). Сброс буфера —
по причинам (перед сохранением сообщения), чтобы не терять хвост.
Батчинг живёт в бэкенде.

**Nocturn:** события идут по одному из Rust, сглаживание на фронте
(streamBuffer + rAF, перф-бюджеты). Для однопроцессной схемы — адекватно.

**Вердикт:** взять формат (seq + eventId + причины сброса) при появлении
фоновых прогонов, когда события пойдут из нескольких источников (план, п.5).

## Паттерн 4 — Идл-очередь задач (offpeak)

**ZCode:** отдельный класс задач — без расписания, исполняются, когда
машина простаивает; живут в том же планировщике, что и cron.

**Nocturn:** автоматизации только по расписанию.

**Вердикт:** дешёвый перенос, полностью локальный (план, п.4). Пул простоя
в Rust: задача с квотой-счётчиком, исполняется при отсутствии активности.

## Паттерн 5 — Хранилище: SQLite-индекс + воркер миграций

**ZCode:** индекс задач в SQLite; миграции хранилища — в worker_threads
с постингом прогресса (валидация входа схемой; done/failed наверх).

**Nocturn:** sessions.json (JSON), миграции инлайн при старте lib.rs.

**Вердикт:** держать в голове; к SQLite переходить, только когда JSON
начнёт тормозить (тысячи сессий). Миграции с прогрессом — паттерн на
будущее. Экспорт у нас whitelist'ом — строго лучше их blacklist'а, не менять.

## Паттерн 6 — Удержание и границы экспорта

**ZCode:** retention-константы (количество + возраст), служебные каталоги
на диске с zon-именами, export-исключения для credential-файлов.

**Nocturn:** storage-менеджер уже есть; whitelist экспорта правильнее.
**Вердикт:** не менять; подсмотреть только идею возрастных лимитов для
логов/статистики, если объёмы вырастут.
